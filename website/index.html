Why a router

No single model drives a robot.

A fold, a hallway, a stop command and a ten-step chore need different models, different compute and different deadlines. Today that logic is hard-coded into every robot stack.

01 · latency

Control loops don't wait

A 30 Hz policy gets 33 ms per step. A cloud round-trip costs seconds. The router knows which models can keep up.

02 · location

Networks drop

Warehouses, farms and basements lose Wi-Fi. Offline robots never call the cloud; degraded links prefer the edge.

03 · safety

Safety is not a model

"Stop" goes to a deterministic controller in milliseconds, before any learned model sees it. Every route ends in a fail-safe.

04 · embodiment

Bodies differ

An arm, a humanoid and a quadruped need different policies. Routing matches each request to models trained for that body.

Default model set

See. Think. Move.

The router ships with a model pool grouped by role. Each request uses the model in the role it needs, on whatever compute it can reach, including your browser.

Install

Get started in one line.

bash
$ pip install git+https://github.com/ddiddi/solo-router
$ export ANTHROPIC_API_KEY=sk-ant-...   # or OPENAI_API_KEY / NEBIUS_API_KEY
$ solo-router run "plan how to clear the table, then wipe it"
[long_horizon_task -> anthropic/claude-sonnet-5-5 @ cloud]
1. move_above(plate) ...
$ solo-router serve --proxy    # OpenAI-compatible on :8899
http
$ curl localhost:8899/v1/chat/completions -d '{
    "model": "solo/auto",
    "messages": [{"role": "user", "content": "hand me the scissors"}],
    "robot": {"embodiment": "arm", "observations": ["rgb"],
              "control_hz": 20, "humans_nearby": true}
  }'
# x-solo-router-decision: realtime_manipulation
# x-solo-router-model:    pi0-3b
# x-solo-router-safety:   elevated  (max 0.25 m/s, 20 N)

Python 3.10+. The server uses only the standard library, so it runs on the robot itself.

Providers

One endpoint. Every model your robot needs.

A unified, OpenAI-compatible API for robot policies and hosted models, with routing, fallbacks and a safety envelope across onboard, edge and cloud. Bring your own OpenAI, Claude or Nebius Token Factory key.

01 · one key

Any one key is enough

Add a key and the router uses that provider for cloud work, and the robot's own models for everything else. No key: it stays self-hosted.

02 · no code changes

Switch models in config

Models are provider/model IDs in one YAML file. Change the pool or the provider, not the robot.

03 · fallbacks

Route around outages

If a provider fails or rate-limits, the request falls through to the next model. Every chain ends at the safety controller.

04 · your keys

No account, no markup

Keys live in your env, a per-request header, or this browser. You pay each provider directly at its own price.

Dry-run mode

Returns the decision and trace without calling any backend. Use it on a laptop, in CI, or to audit a new policy before it touches hardware.

$ solo-router serve

Proxy mode

Forwards chat to OpenAI-compatible backends and observations to policy servers' /act. Falls back down the chain if a backend is unreachable.

$ solo-router serve --proxy
Safety envelope

Your robot. Your safety envelope.

Routing is where safety policy belongs: before any model runs, in code you can read.

  • Stop preempts everything. "Stop", "halt" and e-stop flags go to a deterministic controller at the highest priority.
  • Elevated risk tightens limits. Knives, heat or people nearby cap speed and force, and only higher-tier policies stay eligible.
  • Every chain ends in a fail-safe. If no policy qualifies, the robot holds position instead of guessing.
  • Data stays where you put it. Offline robots never route to the cloud. Camera frames go only to models you list.
